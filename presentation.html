Honest review of the starting idea

"A B2C extension that makes any app voice-powered"

Keep — this is the real insight
  • The extension is the moat. It's the only form factor where the agent already sees what the user sees. No URL to paste.
  • B2C is the right wedge. Zero integration, zero onboarding, works on sites that will never build an assistant.
  • Voice + a live page is genuinely new. Most voice agents are blind to context; most page assistants are silent.
Cut — this framing loses
  • "Voice control any app" has no home for live web data. DOM automation is not web knowledge — you forfeit a whole prize track.
  • "Any app" is unbuildable in 5 hours. A generic DOM-driving agent is fragile and demos badly on stage.
  • It's the crowded lane. Several teams will ship a talking wrapper. Judges asked to be surprised.

Keep the form factor. Change the job. Don't control the page — ground it.

The reframe

Control → Grounding

Before

"Talk to your apps"

Agent's job is to click things for you. Value = saved clicks. Every site needs its own selectors. Live web data is bolted on, if at all. Fails silently when a DOM changes.

After

"Ask the web about this page"

Agent's job is to tell you what this page isn't telling you. Value = an answer you couldn't get by reading. Live web data is the product. Works on any page on day one.

Product

Four things Sidekick does

Each one is a different context.dev capability. That's deliberate.

Ground

"Is this actually a good price?"

Extracts the product on the page, pulls the same product from three other sites live, speaks a verdict — and highlights the number in the page as it talks.

/v1/web/extract · /v1/web/scrape/markdown

Watch

"Tell me if this changes."

Registers a live monitor on the page. When the price, the stock status or the terms move, the agent speaks to you unprompted — even on a different tab.

Monitors API · change.detected webhook

Read

"Just read me this."

Accessibility layer for pages with hostile markup. Clean markdown extraction narrated properly — not a screen reader crawling through nav soup.

/v1/web/scrape/markdown

Dress

Looks native on every site

The overlay pulls the current site's real logo, colours and type, so Sidekick renders in the host brand instead of as a foreign box.

/v1/brand/retrieve · styleguide extraction

The demo — 90 seconds, rehearsed

This is the slide that wins or loses

1
Land on a product page. Hit the hotkey. "Is this a good price?"
Prefetch already ran on page load — the extraction is warm. Agent answers in about two seconds, and a client tool rings the price in the live DOM while it speaks.
2
"Where's it cheaper?" — interrupt it mid-sentence
Interruption is native to the agent loop. Three competitor pages scraped live; a comparison card renders as an overlay in the host site's own brand colours.
3
"Watch this one and tell me if it drops."
A monitor is created on that URL. Confirmed out loud. The user closes the tab and moves on — the agent does not.
4
The page changes. Sidekick speaks first.
Webhook fires into our backend, backend pushes to the extension, the agent says it out loud unprompted: "That listing you were watching just dropped 400 dirhams."
5
Switch to a badly-built local site. "Just read me this."
Closing beat: the same machinery is an accessibility layer for the whole web, not a shopping toy.

Beat 4 is the surprise. An agent that talks to you about a page you already left.

The contract

One schema file. Two consumers.

Tool definitions live in one shared typed package. The backend validates against it, the agent config is generated from it — so names can't drift apart.

Move 1

Prefetch on navigate

The service worker fires the extraction the moment a page loads — long before anyone touches the hotkey. By the time you speak, the answer is a cache read, not a scrape.

Move 2

Speak during the gap

Tools get a spoken pre-roll, so the agent is already saying "let me check that" while the network call is in flight. Dead air is what makes a voice demo feel broken.

Move 3

Answer, then enrich

Cheap answer first from what's already cached; competitor data streams in as a second sentence. Never make the user wait on the slowest call.

The 3.39s → 0.90s gap isn't a footnote. It's the reason the architecture has a prefetch layer at all, and it's the first thing we'll say when the judges read the code.

They said they're judging the codebase

So the repo is a deliverable, not a byproduct

What a judge will find
  • One typed contract for tool schemas, imported by both the backend and the agent config generator. Names cannot drift.
  • No key in the client bundle. Greppable, and we'll invite them to grep it.
  • Tests where the risk is — the tool layer, with recorded vendor fixtures. Not a token test on a helper function.
  • A README that opens with the architecture and the latency numbers that justified it.
  • Small, honest commits across five people, not one 4,000-line dump at 14:20.
How we steer the coding agents
  • Contract first, then fan out. The tool schema is frozen by hand before any agent writes an implementation — that's what makes parallel work merge cleanly.
  • One agent per boundary — extension, backend, tools — because the boundaries are already defined.
  • The prompts are committed. A short log of what we asked for, what came back wrong, and what we changed. "Best Devin Use" is judged on steering, so we show the steering.
  • Humans own the risky hour. The mic spike and the demo script are hand-driven. Agents own the surface area.

The team that can explain why the prefetch layer exists beats the team whose demo happened to work.
